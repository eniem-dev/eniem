## Overview

`products.generated.ts` is your single source of truth for product pricing data. The Eniem CLI generates this file by syncing products from your Polar dashboard, ensuring your UI always displays accurate pricing, features, and product identifiers.

This file is **auto-generated**—you should never edit it manually. When you update products in Polar, run the CLI sync command to regenerate this file.

## Generated Types

The generated file exports TypeScript types that your components consume:

```typescript
// ProductDisplay - Display configuration for UI rendering
export interface ProductDisplay {
  title: string;
  subtitle?: string;
  price: string;
  period?: string;
  badge: string | null;
  features: string[];
  highlighted: boolean;
  cta: string;
}

// GeneratedProduct - Full product identity + metadata
export interface GeneratedProduct {
  slug: string;
  productId: string | null;
  name: string;
  type: "subscription" | "one_time" | "free";
  display: ProductDisplay;
}
```

**Why two types?** `GeneratedProduct` holds the full product identity—slug, Polar product ID, name, and billing type. `ProductDisplay` is a nested object within each product that contains all the UI rendering configuration: formatted prices, feature lists, badges, and call-to-action text. Note that `productId` is `null` for unconfigured products (e.g. production products before Polar IDs are set), which is used by `getCheckoutProducts()` to filter them out.

## Environment Configuration

The generated file exports two product sets:

```typescript
export const sandboxProducts: GeneratedProduct[] = [/* ... */];
export const productionProducts: GeneratedProduct[] = [/* ... */];
```

The `getProducts()` helper selects the correct set based on environment:

```typescript
export function getProducts(env: "sandbox" | "production"): GeneratedProduct[] {
  return env === "sandbox" ? sandboxProducts : productionProducts;
}
```

Pass `env.payment.polarServer` from your app config:

```typescript
import { getDisplayProducts } from "@/features/subscription";
import { env } from "@/config";

const products = getDisplayProducts(env.payment.polarServer);
```

Sandbox products have real Polar `productId` values for testing checkout flows. Production products start with `productId: null` until you configure them in the Polar dashboard—`getCheckoutProducts()` filters these out automatically.

## Data Flow

```
┌──────────────────────────────┐
│    products.generated.ts     │  ← CLI syncs from Polar
└──────────────┬───────────────┘
               │
       ┌───────┴────────┐
       ▼                ▼
┌──────────────┐  ┌──────────────────┐
│ getDisplay   │  │ getCheckout      │
│ Products()   │  │ Products()       │
└──────┬───────┘  └──────┬───────────┘
       │                 │
   ┌───┴────┐            ▼
   ▼        ▼      ┌──────────────┐
┌────────┐ ┌────────────────┐     │ BetterAuth   │
│Pricing │ │ChoosePlan      │     │ checkout     │
│ Page   │ │ Content        │     │ config       │
└───┬────┘ └───┬────────────┘     └──────────────┘
    │          │
    │     (has plan selection?)
    │      ├─ yes → auto-checkout
    │      └─ no  ─┐
    └──────┬───────┘
           ▼
    ┌─────────────┐
    │ PricingCard  │  ← product.display → props
    └──────┬──────┘
           ▼
    ┌─────────────┐
    │  BuyButton   │  ← slug-based checkout
    └─────────────┘
```

**Two consumption paths:**
- **PricingPage** calls `getDisplayProducts(env)` and renders each product as a `PricingCard`. Display fields are mapped to props: `product.display.title` → `name`, `product.display.price` → `price`, `product.display.features` → `features`, etc.
- **ChoosePlanContent** receives the same products. If the URL contains a plan selection (from an unauthenticated BuyButton redirect), it auto-triggers `authClient.checkout()` on mount. Otherwise it falls back to showing PricingCards.

## Product Filtering

Not all products should appear on the pricing page. `getDisplayProducts()` filters products:

```typescript
export function getDisplayProducts(env: "sandbox" | "production") {
  return getProducts(env).filter((p) => p.display.features.length > 0);
}
```

This returns `GeneratedProduct[]`—the full product objects, not just display data. Components then access `product.display.title`, `product.display.price`, etc. for rendering.

**Why filter by `display.features`?** Products without display features are typically internal (API-only checkout) or incomplete. Filtering ensures only customer-facing products with displayable feature lists appear in the UI.

## Checkout Integration

The `BuyButton` component initiates checkout using the product slug:

```tsx
<BuyButton slug={product.slug} label={product.display.cta} />
```

`BuyButton` handles two flows depending on authentication state:

- **Authenticated users**: Calls `authClient.checkout({ slug })` to start a Polar checkout session directly.
- **Unauthenticated users**: Redirects to the signup page with the selected plan encoded in the URL via `appendPlanSelectionToUrl`, so the plan is preserved through registration.

The BetterAuth checkout plugin is auto-configured using `getCheckoutProducts()` (see below), so you don't need to manually list product IDs in your auth config.

**Why slugs instead of product IDs?** Slugs are human-readable and stable across environments. The same slug ("pro-monthly") maps to different Polar product IDs in sandbox vs production.

## Checkout Products

For BetterAuth integration, `getCheckoutProducts()` returns only products with a valid Polar product ID:

```typescript
export function getCheckoutProducts(env: "sandbox" | "production") {
  return getProducts(env)
    .filter((p) => p.productId !== null)
    .map((p) => ({
      productId: p.productId as string,
      slug: p.slug,
    }));
}
```

Products with `productId: null` (unconfigured in the Polar dashboard) are excluded. This array is passed to BetterAuth's `polar.checkout.products` config, ensuring only valid products can initiate payment flows.
