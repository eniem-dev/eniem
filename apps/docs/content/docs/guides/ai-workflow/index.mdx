The AI workflow is an autonomous development system that uses an AI coding CLI to implement features from specifications. It follows a spec-driven approach: define requirements, plan tasks, then build iteratively — producing atomic commits, tested code, and PRs automatically.

## Prerequisites

- `eni` CLI installed (`pnpm add -g @eniem/cli` or as a local dependency)
- At least one AI CLI installed: Claude Code, OpenCode, or Codex (see [Multi-CLI Setup](/docs/guides/multi-cli-setup))
- `bd` (beads) CLI installed (`npm install -g @beads-cli/bd`)
- Beads initialized in the project (`.beads/` directory)

## How It Works

```
specs/*.md → eni plan → beads issues → eni build → committed code + PR
```

- **Specs**: Markdown files describing features, created manually or via `/functional-spec-interview`
- **Plan**: Reads a spec, explores the codebase, and creates a beads epic with decomposed tasks
- **Build**: Picks one ready task per iteration, implements it, validates, commits, and closes the bead

## Quick Start

```bash
# 1. Create a spec
/functional-spec-interview user-authentication

# 2. Plan: generates beads tasks from the spec
eni plan --spec=user-authentication

# 3. Build: implements tasks one at a time
eni build --spec=user-authentication
```

## Initializing AI Workflow

The `eni ai init` command sets up AI workflow files in your project (`.eni/`, `.claude/`, `specs/`, etc.):

```bash
eni ai init
```

Use `--force` to skip confirmation when updating an existing setup:

```bash
eni ai init --force
```

### Git Protocol Flags

By default, `eni ai init` clones boilerplate files via SSH and automatically falls back to HTTPS if the SSH connection times out (10 seconds). You can control this behavior:

| Flag | Description |
| --- | --- |
| `--protocol=ssh` | Force SSH only — no HTTPS fallback on timeout |
| `--protocol=https` | Use HTTPS directly — skip SSH entirely |
| `--https` | Shorthand for `--protocol=https` |
| `--ssh` | Shorthand for `--protocol=ssh` |

**Examples:**

```bash
# Use HTTPS directly (corporate networks, CI/CD with tokens)
eni ai init --https

# Force SSH only, no fallback
eni ai init --ssh

# Equivalent long forms
eni ai init --protocol=https
eni ai init --protocol=ssh
```

**When to use `--https`:**

- Your network blocks SSH port 22 (corporate firewalls)
- CI/CD pipelines using HTTPS tokens for git authentication
- You prefer HTTPS over SSH key management

**Fallback behavior (default, no flag):**

1. Attempts SSH clone
2. If SSH times out after 10 seconds, automatically retries via HTTPS
3. On successful fallback, shows a tip: *"Use --protocol https to skip SSH next time"*
4. If both fail, shows combined error messages from both attempts

The same protocol flags also work with the main `eni [project-name]` scaffolding command.

## Commands Reference

| Command | Description |
| ------- | ----------- |
| `eni plan` | Interactive spec selection, then plan |
| `eni plan --spec=<name>` | Plan a specific spec |
| `eni plan --spec=<name> --iterations=5` | Plan with custom iteration count (default: 3) |
| `eni build` | Interactive spec selection from planned/, then build |
| `eni build --spec=<name>` | Build a specific planned spec |
| `eni build --spec=<name> --iterations=20` | Build with custom iteration count (default: 10) |
| `eni build --verbose` | Build with detailed tool invocation output |

## Plan Mode

Reads a spec, explores the codebase, and creates a beads epic with atomic tasks:

```bash
eni plan --spec=user-authentication
```

- Default: 3 iterations (refines tasks across iterations)
- Output: beads epic with atomic tasks, dependencies, and acceptance criteria
- Spec lifecycle: `specs/<name>.md` → `specs/planned/<name>.md` when planning completes
- Early exit: stops early if tasks are fully refined before max iterations

## Build Mode

Picks one ready task per iteration and implements it end-to-end:

```bash
eni build --spec=user-authentication
```

- Default: 10 iterations
- Each iteration: claim task → implement → test → commit → close bead → push
- Creates a PR when all tasks are complete
- Spec lifecycle: `specs/planned/<name>.md` → `specs/archive/<name>.md` when done
- Early exit: stops early if all tasks complete before max iterations

## Creating Specs

Use `/functional-spec-interview` for guided spec creation:

```bash
/functional-spec-interview analytics-dashboard
```

The interview covers:

1. **Purpose & JTBD**: What job does this feature accomplish?
2. **Target User**: Who uses this feature?
3. **Scope**: What's included and excluded?
4. **Requirements**: Must-have vs nice-to-have
5. **Constraints**: Technical and performance limits
6. **Acceptance Criteria**: Testable success conditions
7. **Edge Cases**: Error states and boundaries

Output is saved to `specs/<feature-name>.md`.

## Slash Commands

### `/functional-spec-interview`

Interactive spec creation through guided questions:

```bash
/functional-spec-interview <feature-name>
```

### `/fix-code-review`

Automatically address GitHub PR review comments:

```bash
/fix-code-review https://github.com/owner/repo/pull/123
```

Process:

1. Fetches review comments from the PR
2. Analyzes and proposes fixes
3. Shows plan for approval
4. Applies approved fixes
5. Validates (build, lint, tests)
6. Detects pattern gaps for AGENTS.md updates

## Guardrails

- **One task per iteration** — Fresh context prevents drift and hallucination
- **Validation required** — Never commit code that fails tests, lint, typecheck, or build
- **Search before implementing** — Always verify functionality doesn't already exist
- **Follow existing patterns** — Match AGENTS.md conventions and existing code style
- **Atomic commits** — Each commit implements exactly one task
- **Tracer bullet first** — First tasks form a minimal end-to-end vertical slice

## Folder Structure

```
repo/
├── .eni/
│   ├── PROMPT_plan.md      # Plan prompt template
│   └── PROMPT_build.md     # Build prompt template
├── .claude/                # Claude Code config (hooks, commands, skills)
├── .opencode/              # OpenCode config (plugins, commands, skills)
├── .codex/                 # Codex config (config.toml)
├── .agents/                # Codex skills
├── .beads/                 # Issue tracking database
├── specs/                  # Feature specifications
│   ├── my-feature.md       # Unplanned specs
│   ├── planned/            # Specs with generated tasks
│   └── archive/            # Completed specs
└── AGENTS.md               # Project conventions (used by all CLIs)
```

For details on each CLI's config structure, see the [Multi-CLI Setup](/docs/guides/multi-cli-setup) guide.

## Workflow Example

```bash
# 1. Create spec via interview
/functional-spec-interview user-dashboard

# 2. Plan the feature
eni plan --spec=user-dashboard

# 3. Check generated tasks
bd ready

# 4. Build iteratively
eni build --spec=user-dashboard

# 5. PR is created automatically when all tasks complete
```
