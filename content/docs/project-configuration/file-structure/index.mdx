## Global Project Structure

```
repo/
├── app/           # Next.js App Router (routes & pages)
├── features/      # Business logic modules
├── lib/           # Shared utilities & abstractions
├── components/    # Reusable UI components
├── hooks/         # Global React hooks
├── config/        # Environment & app configuration
├── locales/       # Internationalization
├── prisma/        # Database schema & migrations
└── public/        # Static assets
```

| Folder        | Purpose                                           |
| ------------- | ------------------------------------------------- |
| `app/`        | Next.js 15 App Router with route groups and pages |
| `features/`   | Self-contained business logic modules             |
| `lib/`        | Cross-cutting utilities (auth, db, logger, email) |
| `components/` | Reusable UI components and shadcn/ui              |
| `hooks/`      | Global React hooks used across the app            |
| `config/`     | Environment variables and app configuration       |
| `locales/`    | Centralized internationalization strings          |
| `prisma/`     | Database schema and migrations                    |
| `public/`     | Static assets (images, fonts, etc.)               |

## App Router Structure

The `app/` directory uses Next.js **route groups** for logical organization without affecting URLs.

```
app/
├── (auth)/           # Authentication pages
│   ├── login/
│   │   └── page.tsx
│   ├── signup/
│   │   └── page.tsx
│   └── layout.tsx    # Auth-specific layout
│
├── (protected)/      # Authenticated user routes
│   ├── dashboard/
│   │   └── page.tsx
│   ├── account/
│   │   └── page.tsx
│   └── layout.tsx    # shared layout
│
├── (marketing)/      # Public marketing pages
│   ├── pricing/
│   │   └── page.tsx
│   └── layout.tsx
│
├── (docs)/           # Documentation site
│   ├── docs/
│   └── layout.tsx
│
└── api/              # API routes
    └── auth/
        └── [...all]/
            └── route.ts
```

### Route Groups Benefits

- **Logical organization**: Group related routes together
- **Shared layouts**: Each group can have its own `layout.tsx`
- **No URL impact**: Parentheses `()` don't affect the URL path
- **Auth separation**: Protected routes can share auth guard layout

## Feature-Based Architecture

Features are self-contained business logic modules. Each feature encapsulates everything related to a specific domain.

### Why Feature-Based?

- **Self-contained**: All related code in one place
- **Clear boundaries**: Easy to understand what belongs where
- **Scalable**: Add new features without touching others
- **Deletable**: Remove a feature by deleting its folder

### Feature Structure

```
features/billing/
├── index.ts           # Public API exports
├── components/        # Feature-specific UI
│   ├── billing-overview.tsx
│   └── subscription-status-card.tsx
├── models/            # Type definitions
│   └── billing.model.ts
├── queries/           # Data fetching
│   └── billing.query.ts
├── services/          # Business logic
│   └── billing.service.ts
├── actions/           # Server actions
│   └── billing.action.ts
└── schemas/           # Zod validation
    └── billing.schema.ts
```

### Public API Pattern

Each feature exports a clean API through `index.ts`:

```ts
// features/billing/index.ts
export { BillingOverview, SubscriptionStatusCard } from "./components";
export { getBillingData } from "./queries";
export { type BillingModel } from "./models";
```

This allows clean imports:

```ts
// In a page or component
import { BillingOverview, getBillingData } from "@/features/billing";
```

## File Naming Conventions

All files use **kebab-case** with typed suffixes to indicate their purpose.

| Suffix        | Purpose                     | Location                | Example                      |
| ------------- | --------------------------- | ----------------------- | ---------------------------- |
| `.action.ts`  | Server actions              | `features/*/actions/`   | `subscribe.action.ts`        |
| `.query.ts`   | Data fetching (server)      | `features/*/queries/`   | `billing.query.ts`           |
| `.schema.ts`  | Zod validation schemas      | `features/*/schemas/`   | `auth.schema.ts`             |
| `.model.ts`   | TypeScript type definitions | `features/*/models/`    | `subscription.model.ts`      |
| `.service.ts` | Business logic services     | `features/*/services/`  | `github-benefits.service.ts` |
| `.util.ts`    | Utility functions           | `features/*/` or `lib/` | `billing.util.ts`            |
| `.tsx`        | React components            | `components/`           | `pricing-card.tsx`           |

### Examples

```
# Server action for newsletter subscription
features/landing-mode/actions/subscribe.action.ts

# Query to fetch billing data
features/billing/queries/billing.query.ts

# Zod schema for authentication
features/authentication/schemas/auth.schema.ts

# Type definitions for subscription
features/subscription/models/subscription.model.ts
```

## When to Use Folders vs Flat Files

### Use Folders When

- **2+ files of same type** in a feature
- **Multiple related concerns** (models, queries, services)
- **Feature has growing complexity**

Example with folders:

```
features/billing/
├── components/
│   ├── billing-overview.tsx
│   └── subscription-status-card.tsx
├── models/
│   └── billing.model.ts
├── queries/
│   └── billing.query.ts
└── services/
    └── billing.service.ts
```

### Use Flat Files When

- **Single file** of a type
- **Simple feature** with limited scope
- **General utility** in `lib/`

Example with flat files:

```
features/settings/
├── index.ts
├── settings.action.ts      # Just one action
├── settings.schemas.ts     # Just one schema
├── settings.types.ts       # Just one types file
└── components/             # Multiple components → folder
    ├── profile-form.tsx
    └── password-form.tsx
```

### Decision Rule

> Start flat, create folders when you have 2+ files of the same type.

## lib/ vs features/

### Use `lib/` for

- **Cross-cutting utilities** used everywhere
- **Third-party integrations** (Polar, Resend, PostHog)
- **Project-wide abstractions** (logger, tracking)
- **No business domain logic**

```
lib/
├── auth.ts              # BetterAuth configuration
├── auth-client.ts       # Client-side auth utilities
├── db.ts                # Prisma client instance
├── logger.ts            # Logging abstraction
├── tracking.ts          # Analytics abstraction
├── email.ts             # Email sending utilities
├── safe-action.ts       # Server action utilities
└── server-handler.ts    # Server handler utilities
```

### Use `features/` for

- **Business-specific logic** tied to a domain
- **Domain-related components** and UI
- **Feature-scoped queries/actions**
- **Self-contained modules**

```
features/
├── authentication/      # Login, signup, password reset
├── billing/             # Subscription management, invoices
├── benefits/            # Downloadables, GitHub benefits
├── settings/            # User profile, account settings
└── subscription/        # Subscription status, plans
```

### Decision Rule

> If it's domain-specific, put it in `features/`. If it's used across multiple domains, put it in `lib/`.

## Component Architecture

### Smart Components

Located in `features/*/components/`, smart components:

- Handle business logic
- Fetch data from server
- Manage state
- Are feature-specific

```tsx
// features/billing/components/billing-overview.tsx
export async function BillingOverview() {
  const billing = await getBillingData();

  return (
    <Card>
      <CardHeader>
        <CardTitle>Billing</CardTitle>
      </CardHeader>
      <CardContent>
        <SubscriptionStatusCard status={billing.status} />
      </CardContent>
    </Card>
  );
}
```

### Dumb Components

Located in `components/` or `components/ui/`, dumb components:

- Pure UI rendering
- Receive data via props
- No business logic
- Reusable across features

```tsx
// components/ui/card.tsx (shadcn/ui)
export function Card({ children, className }) {
  return <div className={cn("rounded-lg border bg-card", className)}>{children}</div>;
}
```

### Component Locations

```
components/
├── ui/                        # shadcn/ui primitives (dumb)
│   ├── button.tsx
│   ├── card.tsx
│   └── input.tsx
├── pricing-card.tsx           # App-specific reusable (dumb)
├── footer.tsx                 # Layout component (dumb)
└── providers/                 # Context providers

features/billing/
└── components/
    └── billing-overview.tsx   # Feature-specific (smart)
```

### Decision Rule

> If a component fetches data or handles business logic, it goes in `features/`. If it's pure UI, it goes in `components/`.
