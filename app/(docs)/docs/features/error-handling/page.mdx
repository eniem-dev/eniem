# Error Handling

ENIEM provides a layered error handling system with custom error classes, centralized server-side processing, and a client-side error boundary.

## Error Classes

Custom error classes in `lib/errors.ts` provide typed errors with HTTP status codes.

| Class              | Status Code | Default Message      |
| ------------------ | ----------- | -------------------- |
| `ServerError`      | 500         | (custom)             |
| `UnauthorizedError`| 401         | `"Unauthorized"`     |
| `ValidationError`  | 400         | `"Validation failed"`|

```ts
// lib/errors.ts
export class ServerError extends Error {
  constructor(message: string, public statusCode: number = 500) {
    super(message);
    this.name = "ServerError";
  }
}

export class UnauthorizedError extends ServerError {
  constructor(message: string = "Unauthorized") {
    super(message, 401);
    this.name = "UnauthorizedError";
  }
}

export class ValidationError extends ServerError {
  constructor(message: string = "Validation failed") {
    super(message, 400);
    this.name = "ValidationError";
  }
}
```

## Server-Side Error Handling

The `handleError` function in `lib/server-handler.ts` processes errors and returns appropriate HTTP responses.

### Error Processing Order

1. **UnauthorizedError** → 401, logged as error
2. **ValidationError** → 400, logged as warning
3. **ServerError** → custom status code, logged as error
4. **ZodError** → 400, first issue message extracted, logged as warning
5. **Generic Error** → 500, logged as error with stack trace
6. **Unknown** → 500, uses `locales.errors.unhandledError`

### Response Formats

**Server Queries** (`createQuery`, `createAuthenticatedQuery`):

```ts
type ServerResponse<T> =
  | { data: T; error: null }
  | { data: null; error: string };
```

**API Handlers** (`createApiHandler`, `createAuthenticatedApiHandler`):

```ts
type ApiResponse<T> =
  | { success: true; data: T }
  | { success: false; error: string };
```

## Error Boundary

The `app/error.tsx` component catches runtime errors in the React tree and displays a user-friendly error page.

```tsx
// app/error.tsx
"use client";

export default function Error({
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <>
      <Navbar />
      <main>
        <p>{locales.ErrorPage.code}</p>
        <h1>{locales.ErrorPage.title}</h1>
        <p>{locales.ErrorPage.description}</p>
        <button onClick={() => reset()}>
          {locales.ErrorPage.tryAgain}
        </button>
        <Link href="/">{locales.ErrorPage.backToHome}</Link>
      </main>
      <Footer />
    </>
  );
}
```

The `reset()` function re-renders the route segment, allowing recovery from transient errors.

## Usage

### Throwing Errors in Handlers

Throw custom errors inside handlers. The `handleError` function catches them and returns the appropriate response format.

```ts
import { UnauthorizedError, ValidationError, ServerError } from "@/lib/errors";

// In a server query or API handler
export const getResource = () =>
  createAuthenticatedQuery(async ({ user }) => {
    const resource = await db.resource.findUnique({ where: { userId: user.id } });

    if (!resource) {
      throw new ServerError("Resource not found", 404);
    }

    if (!resource.isValid) {
      throw new ValidationError("Resource is invalid");
    }

    return resource;
  });
```

### Handling Responses

Both server queries and API handlers return discriminated unions. Check the `error` or `success` field before accessing data.

```ts
// Server queries
const result = await getResource();
if (result.error) {
  // Handle error
  console.error(result.error);
  return;
}
// Use result.data

// API responses
const response = await fetch("/api/resource");
const json = await response.json();
if (!json.success) {
  // Handle error
  toast.error(json.error);
  return;
}
// Use json.data
```

### Server Actions

Server actions using NextSafeAction return a different error structure with `serverError` and `validationErrors`.

```ts
const result = await updateProfileAction({ name: "John" });

if (result?.serverError) {
  // serverError is a string message from handleServerError
  toast.error(result.serverError);
  return;
}

if (result?.validationErrors) {
  // Field-level validation errors from Zod schema
  console.log(result.validationErrors);
  return;
}

// Success - use result.data
```

With the `useAction` hook:

```tsx
const { execute, isPending } = useAction(updateProfileAction, {
  onSuccess: ({ data }) => {
    toast.success("Updated!");
  },
  onError: ({ error }) => {
    toast.error(error.serverError ?? "Something went wrong");
  },
});
```

### Type Guards

Use the provided type guard functions for cleaner TypeScript narrowing. These helpers ensure `data` is properly typed after the check.

```ts
import { isServerResponseSuccessful, isApiResponseSuccessful } from "@/lib/server-handler";
import { isActionSuccessful } from "@/lib/safe-action";

// Server queries
const result = await getResource();
if (isServerResponseSuccessful(result)) {
  // result.data is typed, result.error is null
}

// API responses
if (isApiResponseSuccessful(response)) {
  // response.data is typed, response.success is true
}

// Server actions
const actionResult = await subscribeAction({ email: "user@example.com" });
if (isActionSuccessful(actionResult)) {
  // No serverError or validationErrors
  console.log(actionResult.data);
}
```

### resolveActionResult

Promise wrapper that throws on failure, useful for async/await patterns:

```ts
import { resolveActionResult } from "@/lib/safe-action";

try {
  const data = await resolveActionResult(
    subscribeAction({ email: "user@example.com" })
  );
  // data is the successful result
} catch (error) {
  // error is the serverError message
  toast.error(error as string);
}
```
